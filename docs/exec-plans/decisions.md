# Decisions

POC choices for the scenario-1 proof of concept. These are not a steward acceptance line.

1. Scope is scenario 1 only, plus the seed data it needs. Ada, Ben, and Cam are the users. Cable at unit price 10 and Lamp at unit price 5 are the products. PDF export, CSV export, counts, uc32, user CRUD, product CRUD screens, and estimate CRUD beyond creating an estimate in scenario 1 are out of this proof of concept.
2. Replaced by the steward's later rule. A contact belongs to a user. Creating a contact assigns it to the current acting user. The kanban, the contact list, and the estimate list show only that user's contacts, and only estimates whose contact belongs to that user. Switching the dropdown changes which contacts and estimates are visible. Products stay shared. Opening or changing another user's contact is refused with 404. The selected user id is stored in the session under `acting_user_id`. If none is selected, the page asks for a choice, those lists are empty, and state-changing actions are refused with code `user.required` and no row is written.
3. uc3 with an empty contact email is refused with code `contact.email.required`. The column stays `qualified`. No email is recorded.
4. A contact may have more than one estimate. The first successful send sets column to `estimate sent`. Later sends leave it there.
5. Protection levels stay unnamed. The CRM log line does not include the email address or the body. The contact page may show name, email, company, column, and the text `This is a test.` after a send.
6. Mail delivery for the proof of concept is Laravel's log mailer. A sent-email row stores the to address and the body `This is a test.` The contact page shows that body as plain text. No SMTP server is required. The log mailer writes the message to Laravel's log as its delivery record. The CRM log line stays the five fields `feature_id`, `correlation_id`, `actor_id`, `outcome`, and `code`.
7. Non-goals of this proof of concept: speech, passwords, login, Fortify, a fancy email view, decorative effects, payments, attachments, teams, API tokens, a second mail channel, PDF, CSV, counts, uc32.
8. Leave complexity-score, complexity-ceiling, diff-posture, instruction-model, asvs-level, secret-scan-command, SLO fields, page size, payload, timeout, rate limit, near-duplicate-reporter, agents-md-line-budget, and codeowners as `unset` in the constitution. No numbers were invented for them.
9. Empty name on create is refused with code `contact.name.required` and no contact row. That is the one refusal paired with the happy path.
10. The app, Vite, and Postgres run under Docker Compose. `./init.sh` is that boot. It builds the app image, migrates, seeds, and starts the containers. A second run does not drop the database. The app container talks to Postgres by the service name `postgres`. The application connection stays `pgsql` and the database name stays `just_tell_crm`. Docker is the runtime. The host does not need PHP, Composer, or Node for the app to boot.

## Notes that follow from those choices

- `laravel/react-starter-kit` 1.0.1 does not ship the Fortify package. It ships hand-rolled login, registration, and password reset. Those routes and screens are removed. `login-mechanism` is none. The acting user is the session id, not the `auth` middleware, because that middleware would redirect to a login screen this product does not have.
- The kit's test runner is PHPUnit. The proof of concept uses that runner. `phpunit.xml` uses sqlite in memory. The application runtime connection stays `pgsql`. Compose sets `DB_HOST=postgres` and leaves the other database settings in `.env`. `tests/bootstrap.php` copies PHPUnit's sqlite values onto `$_SERVER`, because Laravel reads that first and a container `DB_CONNECTION` would make `RefreshDatabase` wipe Postgres.
- Nothing was listening on port 5432. The first compose file started only Postgres. The image is `postgres:18` with `pull_policy: never`, because that image was already on this machine. Docker Hub credentials could not pull `postgres:16`. The data directory is the named volume `pgdata`, mounted at `/var/lib/postgresql`, which is the path Postgres 18 expects. The cluster files live in that volume, outside the repository. A host folder `.pgdata` was used while the Docker disk was full. The install command does not start the database. `init.sh` does not delete the volume.
- The later container decision replaces that postgres-only file with `docker-compose.yml`. Docker Hub still has no username, so `./init.sh` builds from `php:8.4-cli` when that image is local, and otherwise from the local FrankenPHP image `ratatosk-app:latest` (PHP 8.4.27, Composer, `pdo_pgsql`, `pdo_sqlite`). Node 22 is downloaded from nodejs.org during the image build. `compose.yaml` is removed so Compose does not keep using the postgres-only file.
- Qualify may store an empty email and still move a `new` contact to `qualified`, so a later send can hit `contact.email.required`. A contact that is already `qualified` or `estimate sent` keeps that column when qualify is submitted again.

11. Draft use cases uc4–uc31 are in this slice. uc32 stays out. Scenario 1 paths and route names stay: `home`, `acting-user.store`, `contacts.index`, `contacts.store`, `estimates.index`, `contacts.show`, `contacts.qualify`, `contacts.estimates.store`.
12. Constitution `page-size` is 15. List search uses `q` and matches name only. On the estimate list that name is the contact name. Previous and next links come from the page props.
13. The count on a list is the whole scoped set. It ignores `q` and the current page. Users and products count every row. Contacts and estimates count the acting user's rows. With no acting user, every list is empty and the count is 0.
14. CSV downloads the rows matching `q`, or the whole scoped set when `q` is empty. It is not limited to the current page. Columns match the list. Contact CSV is name and column. Email stays off the contact list and off the contact CSV.
15. PDF is the detail page as a PDF through `barryvdh/laravel-dompdf`. One Blade view renders plain fields. Contact PDF may include email, company, column, and `This is a test.` after a send. The domain does not import the PDF library.
16. Any acting user may create, update, and delete users and products. Contacts and estimates stay owned by the user who created the contact. Opening or changing another user's contact or estimate is 404. A missing user or product is 404. A show with no acting user is 404.
17. Deleting a user who still owns a contact is refused with `user.delete.blocked` and no row is removed. Deleting a user who owns none removes the user and clears `acting_user_id` when it was that user.
18. Deleting a contact removes that contact, its estimates, its estimate lines, and its sent emails. Deleting an estimate removes that estimate and its lines. The contact column does not move backward. The sent-email row stays on the contact.
19. Deleting a product that is on an estimate line is refused with `product.delete.blocked`. A product price change does not rewrite stored line prices or past grand totals.
20. Contact update can change name, email, and company. Empty email and company are allowed. The column does not change and no mail is sent. Estimate update replaces lines. At least one quantity must be 1 or more, or the code is `estimate.lines.required`. The grand total is the sum of quantity times the current product unit price, and the stored line unit price becomes that current price. No mail is sent and the column does not change.
21. Contact and user create move off the list onto their own pages. The estimate list gains a send form that uses the same action as the contact page. uc8 remains the contact create. uc16 remains that send. The next step after this slice is a fixture factory. This slice does not build it.
